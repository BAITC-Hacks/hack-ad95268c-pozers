# Предлагаемый контракт UI ↔ backend, версии demo/v1 + расширение v2

**Не согласованный API команды и НЕ документация ekt.kz.**
Этот контракт создан для независимой проверки интерфейса. Backend-команда должна согласовать
его либо изменить адаптер `public/api.js` под собственный контракт.

## Общие правила

Базовый путь `/api`, один домен с интерфейсом. Все ответы — JSON, без кэширования.
Сессия — серверная, cookie с HttpOnly и SameSite; в HTTPS обязателен Secure.
GET `/session` создаёт или возвращает сессию и выдаёт CSRF-токен.
POST-запросы передают токен в `X-CSRF-Token`, данные — `Content-Type: application/json`.
Сервер не доверяет user_id, цене, остатку или составу корзины из браузера.
Настоящие секреты магазина и AI никогда не выдаются в UI.

Все изменяющие/повторяемые операции получают `request_id` — UUID, созданный один раз.
При повторе после ошибки используются тот же UUID и те же данные. Другие данные с тем же UUID → 409.
Одно подтверждение предложения не может изменить корзину дважды, даже с новым UUID.

Общая ошибка (HTTP 4xx/5xx):

```json
{"error":{"code":"INSUFFICIENT_STOCK","message":"Остаток изменился. Нужно новое предложение."}}
```

UI имеет тайм-аут 12 секунд. Тайм-аут не доказывает, что операция не выполнилась.
Окончательный backend должен обеспечивать идемпотентность и атомарность в постоянном хранилище.

## Маршруты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/session` | Сессия, CSRF, режим данных и активное предложение |
| POST | `/chat` | Запрос покупателя и карточки, без изменения корзины |
| POST | `/cart/proposals` | Подготовить конкретное предложение, без добавления |
| POST | `/cart/confirm` | Подтвердить и выполнить добавление |
| POST | `/cart/cancel` | Отменить предложение, не редактируя корзину |
| GET | `/cart` | Актуальная корзина этой сессии |

### GET /session

```json
{"csrf_token":"server-generated-token","data_mode":"demo","proposal":null}
```

`data_mode`: `demo` либо `live`. Без скрытого переключения реальных данных на синтетические.
`proposal`: активное неподтверждённое предложение этой сессии или `null`.
UI восстанавливает его после обновления страницы.

### POST /chat

Запрос:

```json
{"message":"Нужен автомат C16","request_id":"UUID"}
```

Ответ:

```json
{
  "message":"Нашёл позицию в учебном каталоге.",
  "products":[{
    "id":"demo-001",
    "sku":"DEMO-001",
    "name":"Автоматический выключатель C16",
    "specs":["16 А","1 полюс","6 кА"],
    "price":2850,
    "currency":"KZT",
    "stock":24,
    "unit":"шт.",
    "kind":"breaker",
    "certificate_url":null
  }],
  "result_type":"products",
  "proposal":null,
  "cart_url":"#cart",
  "data_mode":"demo",
  "warnings":[]
}
```

`result_type`: `products`, `empty`, `terms` или `message`.
В пустом поиске `products: []`, `result_type: "empty"`. В ответе об условиях список тоже может быть пуст,
но `result_type: "terms"`: отсутствие карточек само по себе не ошибка поиска.
`stock: null` означает неизвестный остаток, а не ноль. Кнопка выбора заблокирована в обоих случаях.
`kind` определяет нейтральную иллюстрацию: `breaker` или `cable`; это не фотография товара.
Для аналога можно добавить строковое поле `reason` с обоснованием.
`certificate_url`: предоставленная сервером HTTP(S)-ссылка либо null. UI не выдумывает документы.
Текст рассматривается как текст, а не доверенный HTML.

### POST /cart/proposals

```json
{"product_id":"demo-001","quantity":2,"request_id":"UUID"}
```

Ответ:

```json
{
  "proposal":{
    "id":"server-proposal-uuid",
    "status":"pending",
    "product_id":"demo-001",
    "sku":"DEMO-001",
    "name":"Автоматический выключатель C16",
    "quantity":2,
    "unit":"шт.",
    "unit_price":2850,
    "total":5700,
    "currency":"KZT",
    "warehouse":"Учебный склад · не ekt.kz",
    "expires_at":"2026-09-23T10:05:00.000Z"
  },
  "data_mode":"demo"
}
```

Дата выше — только пример. Сервер выдаёт действительный срок относительно своего времени.
Цену и товар определяет сервер, не браузер. Предложение связано с сессией и имеет срок действия.
Демо допускает одно актуальное предложение на сессию; другие запросы отклоняются до отмены/подтверждения.
Количество учитывает уже лежащее в корзине количество и остаток. Подготовка не изменяет корзину.

### POST /cart/confirm

```json
{"proposal_id":"server-proposal-uuid","request_id":"UUID"}
```

Единственный успешный формат:

```json
{
  "status":"confirmed",
  "proposal_id":"server-proposal-uuid",
  "cart":{
    "items":[{
      "product_id":"demo-001",
      "sku":"DEMO-001",
      "name":"Автоматический выключатель C16",
      "kind":"breaker",
      "quantity":2,
      "unit":"шт.",
      "unit_price":2850,
      "total":5700
    }],
    "total":5700,
    "currency":"KZT",
    "revision":1,
    "cart_url":"#cart"
  }
}
```

`revision` — монотонно возрастающая версия корзины. UI не откатывается к более старому ответу.
UI показывает успех только после HTTP 2xx, точного `status: confirmed`, совпадения proposal_id
и проверки структуры/сумм корзины. Повтор подтверждения возвращает актуальную корзину без повторной записи.
Перед записью сервер снова проверяет сессию, срок, цену и итоговое количество.
Изменения цены/количества требуют нового предложения и нового согласия, не молчаливой замены.

### POST /cart/cancel

```json
{"proposal_id":"server-proposal-uuid","request_id":"UUID"}
```

Ответ:

```json
{"status":"cancelled","proposal_id":"server-proposal-uuid"}
```

Повторная отмена безопасна. Уже выполненное добавление не отменяется этим маршрутом:
возвращается `409 ALREADY_CONFIRMED`. Удаление из корзины — отдельная будущая функция.

### GET /cart

```json
{"cart":{"items":[],"total":0,"currency":"KZT","revision":0,"cart_url":"#cart"}}
```

Непустая структура совпадает с полем `cart` ответа подтверждения.
`cart_url` должен вести на эту же корзину/сессию, а не просто на главную страницу магазина.
Текущая реализация использует внутреннюю hash-страницу `#cart` и не принимает внешние URL корзины.
Сумма доставки не включена; UI явно указывает, что доставка не рассчитана.

## Что заменить при настоящей интеграции

`server-demo.mjs` — только имитатор с памятью одного процесса. Его не нужно переносить внутрь
backend другого участника как якобы готовую интеграцию магазина.
Нужны подтверждённые источники данных, сессии сайта, транзакции/идемпотентность в БД,
документированный адаптер настоящей корзины, ограничения частоты запросов, политика хранения данных,
проверенная обработка денежных значений, мониторинг и тесты настоящей интеграции.
Никакой маршрут данного файла не заявляется как существующий маршрут ekt.kz.

# Расширение v2: Ревизор и доказательства

Это всё ещё **предлагаемый** контракт, не согласованный API ekt.kz.
Однотоварные запросы v1 сохранены, но frontend v2 также ожидает следующие возможности.

## Provenance: источники и ограничения

Товар, ответ чата, предложение, корзина, отчёт и сравнение могут включать `provenance`:

```json
{
  "source": {"id":"demo:catalog","label":"Локальный учебный каталог","url":null},
  "fetched_at":"2026-09-23T10:00:00.000Z",
  "data_mode":"demo",
  "fields":["price","stock"],
  "limitations":["Учебные данные, не сведения ekt.kz."]
}
```

Дата выше — пример схемы. Реальный timestamp формирует сервер при чтении.
При повторе request_id исходный timestamp сохраняется. Для live-интеграции нужно
разделять чтение источника, возраст кэша и время изменения данных источника,
не подменять всё текущим временем UI. Возможные метки отображения:
`demo`, `live`, `cached`, `unknown`. Без provenance UI явно сообщает об отсутствии источника.
URL источника показывается только с безопасным HTTP(S)-протоколом.
Не указывайте URL с ключами, авторизацией, временным доступом к персональным данным.

## POST /audit

```json
{"text":"DEMO-001 ; 2 шт.\nDEMO-003 ; 10 м","request_id":"UUID"}
```

Возвращает `{id, rows, provenance, data_mode, message}`.
Строка содержит `id`, `raw`, `sku` (когда распознано), `quantity`, `product`, `status`,
`message`, `alternatives`. У распознанного товара есть `already_in_cart`,
`available_to_add`; `null` означает неизвестное наличие.
Статусы: `ready`, `shortage`, `out_of_stock`, `unknown`, `not_found`, `unparsed`, `unit_mismatch`.
До 10 входных строк, до 6000 символов. В текущем парсере только DEMO-артикул,
разделитель `;`, `:`, `—`, `-`, `x` или `×`, положительное целое количество и опциональная единица.
Дубли одного артикула/единицы объединяются; общее количество сверяется с остатком.
Операция ничего не добавляет и не создаёт предложение. Текст не выполняется как команда.

Каждый `alternatives[]` содержит `{product, comparison}`.
`comparison`: `original_sku`, `candidate_sku`, `parameters`, `status`, `explanation`, `provenance`.
Параметр: `{key,label,original,candidate,verdict}`; verdict = `match`, `different`, `unknown`.
Status = `incompatible` или `requires_review`. Это не сертификация совместимости.
В ответе `/chat` есть необязательный `comparisons[]` с той же таблицей.

## POST /cart/proposals: список

```json
{"items":[{"product_id":"demo-001","quantity":2},{"product_id":"demo-003","quantity":10}],"request_id":"UUID"}
```

Предложение содержит `items`, `total`, `currency`, `id`, `status`, `name`, `sku`,
`warehouse`, `expires_at`, `provenance`.
Каждый элемент `items`: `{product_id,sku,name,kind,quantity,unit,unit_price,total}`.
Для одной позиции старые однотоварные поля также сохранены.
Для нескольких позиций нельзя полагаться на верхнеуровневый product_id/quantity.
Новые UI/валидатор суммируют `items`, не складывают штуки и метры.

Подтверждение и отмена используют прежние маршруты и ID предложения.
Все проверки выполняются до любой записи: ошибка одной позиции отклоняет весь список.
Fingerprint request_id учитывает вложенные items, а не только верхние ключи JSON.
Для production нужны транзакции и сохранённая идемпотентность, не Maps этого демо.

Точная команда `да, добавь` при видимом предложении обрабатывается UI как явное
действие человека и отправляется в `/cart/confirm`. `/chat` не меняет корзину.
Введённые документы/списки никогда не передаются в обработчик пользовательского подтверждения.

## GET /session: поля v2

Добавлены `build` и `diagnostics_enabled`.
Диагностика в UI доступна только при `data_mode: demo` и `diagnostics_enabled: true`.

## POST /demo/checks — только учебный стенд

```json
{"suite":"core","request_id":"UUID"}
```

`suite`: `core` (12 проверок), `repeat` (пять подтверждений), `refusal` (показательный отказ).
Ответ: `run_id`, `build`, `suite`, `scope: isolated-local-demo`, `started_at`, `finished_at`,
`checks`, `summary: {total,passed,failed}`, `limitations`.
Проверка содержит `id`, `name`, `expected`, `observed`, `passed`, `duration_ms`, `trace`.
Трасса содержит метод, путь, HTTP-статус и безопасные идентификаторы; не cookie или CSRF.

При запуске создаётся отдельный локальный сервер и отдельные сессии; после проверки
он закрывается. Корзина вызывающего пользователя не используется. Внешняя цель
не настраивается. Одновременно разрешён один запуск, есть минимальный интервал.
При `DEMO_DIAGNOSTICS=off` маршрут возвращает 404. Не включайте его в настоящем магазине.
